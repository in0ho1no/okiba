# 私物管理ツール 仕様書

本書は、claude.ai上での仕様検討の結果に、AIエージェントによる仕様レビュー（2026年10月）の決定事項を反映したものです。以降の設計・実装はローカルPC上のClaude Codeで行います。

同じ規則は1か所にだけ記載し、他の箇所からは節名（「」で囲む）で参照する。

---

## 目的

私物（書籍、PC関連品、文具など多岐にわたる物品）について、次のことを容易にする。

- どの箱がどこに保管されているか、箱の中身は何かを把握する
- 出し入れ・移動・貸出・手放し（売却・廃棄）の際に記録を更新する
- 後から「何を持っていたか」「どこにあるか」「何本持っているか」を検索する
- 在庫の把握により、既に持っている物を無駄に買い足すことを防ぐ

## 前提と基本方針

- ローカルPCで動作するツールとする。 claude.aiなど特定サービス上には構築しない（契約依存・サービス終了のリスクを避けるため）。
- 形態はローカルWebアプリ（Pythonのサーバー＋ブラウザ）。当面はPCのブラウザから利用する。将来、同一LAN内のスマホから利用できる余地を残す。
- データはSQLite＋画像フォルダで保持し、CSV/JSONへのエクスポートを可能にする。ツールが使えなくなってもデータが残ることを重視する。
- 写真の入手経路：スマホ（主にiPhone）で撮影 → Google Photos → PCにダウンロードしたフォルダから取り込む。Google PhotosのAPIには依存しない。
- 外部サービスへの依存は最小限にし、差し替え可能にする（詳細は「外部連携」）。
- 開発者は Python ツールチェーン（uv, ruff, mypy, pytest）の利用経験あり。これを前提に構成してよい。

## やらないこと（検討の結果、見送った事項）

| 項目 | 理由 |
| --- | --- |
| 背表紙写真などからの一括登録 | 1品ずつ画像を残す運用の方が効率的。一括読み取り→確認→追記は二重作業になるため |
| クラウドAIによる文字認識 | 私物の写真を外部に送らない。サービス依存も避ける。文字認識自体も本命ではない |
| 自動バックアップ | 容量の逼迫や処理のボトルネック化を避けるため。手動で行う |
| 通常操作での物理削除 | 誤操作防止と履歴保全のため。誤登録削除は論理削除とする |
| 初期段階でのQRコードラベル | 当面PC利用のため読み取る場面が少ない。文字ラベルで運用する |
| 初期段階での分割・統合の取消 | 関連する登録の数量や、その後の移動・貸出との整合性維持が複雑になるため。履歴からの差し戻しでも数量や統合関係は戻さない |
| 初期段階でのカテゴリ・保管場所の統合 | テンプレート、子階層、ラベルIDの扱いが複雑になるため。物品のカテゴリ変更・移動で整理する |
| 既存リストからの一括取り込み | 既存の私物をリストで管理していないため |

## 用語

| 用語 | 意味 |
| --- | --- |
| 登録 | 物品1件分のレコード（単位は「登録単位」参照）。物品を新規に記録する操作も指す |
| 所持中 | 状態が保管中・使用中・貸出中のいずれかであること |
| 手放し | 売却・廃棄の操作。売却済・廃棄済の物を「手放した物」と呼ぶ。貸出は手放しに含めない |
| 戻し先 | 使用中・貸出中の物について保持する保管場所。「戻す」「返却」で戻る先 |
| 所在 | 保管中の物では保管場所、使用中・貸出中の物では戻し先 |
| 削除済み | 誤登録削除により論理削除された登録 |
| 統合済み | 統合により統合元となった登録 |
| 廃止 | カテゴリ・タグ・保管場所・項目定義を、データを残したまま新規選択の候補から外すこと |
| 有効 | 削除済み・統合済み・廃止済みのいずれでもないこと |

状態名は「保管中・使用中・貸出中・売却済・廃棄済」と表記する（「売却済み」とは書かない）。

## 機能要件

### 画面構成

最上位で次の3つを切り替える。

- 登録
- 検索・更新（検索結果から詳細画面を開いて各操作を行う。操作の一覧は「検索・更新」）
- 管理（カテゴリとテンプレート、タグ、保管場所。内容は「管理画面と廃止」）

### 登録フロー（段階表示）

入力を進めるごとに次の項目が表示される方式とする。

1. 大カテゴリを選択：過去の登録履歴から候補を表示。該当がなければ新規カテゴリを作成。
2. 小カテゴリを選択：同上。小カテゴリは省略できる（大カテゴリのみで登録可）。
3. カテゴリ別の詳細入力：カテゴリに紐付くテンプレート（「カテゴリとテンプレート」参照）に従って入力欄を表示。
4. 共通項目：名称（必須）、保管場所（必須）、数量（既定値1）、タグ、備考。
5. 登録：「登録」または「登録して同じ内容で続ける」（複製登録）。

名称は全カテゴリ共通の必須項目とする。書籍はタイトルを名称として使う（タイトル欄と名称欄を兼ねる）。ケーブル類の名称は自動生成する（「ケーブル類の固定処理」参照）。

カテゴリ別の流れの例は次のとおり。フェーズ1は手入力のみとし、画像からの読み取りと照会はフェーズ2以降で追加する。

- 書籍
  1. 画像を取り込む（表紙・裏表紙）
  2. 裏表紙のバーコードからISBNを読み取り、書誌情報を照会（フェーズ2）
  3. 照会成功 → タイトル・著者・出版社などを自動入力（修正可）
  4. 照会失敗 → 各入力欄を表示して手入力（ISBNは任意入力）
- ケーブル類
  1. 端子A、端子B、長さを手入力（端子は過去の入力値から選択可能にする）
  2. 画像は任意
  3. 既に同じ物が登録されていれば警告する（「重複警告と集計」参照。例：「同じ端子の組み合わせを2件・計3本登録済み（箱A-03に保管中2本、箱B-01を戻し先として貸出中1本）」）
- 新規カテゴリ
  1. 画像を取り込む
  2. 製品バーコード（JAN）を読み取り、照会（フェーズ3）
  3. 照会成功 → 名称・メーカーなどを自動入力
  4. 照会失敗 → 最低限の入力欄（名称）を表示
  5. 入力欄が足りなければ「項目を追加」で任意の項目を追加
  6. 追加した項目は、そのカテゴリのテンプレートとして保存できる（既定でオン）

入力補助として、次の機能を設ける。

- 各入力欄にクリアボタン（×）を付ける。 複製登録時に、残したい部分は流用し、変えたい欄だけ消して打ち直せるようにする。
- 必須項目の検査：登録・内容編集・履歴からの差し戻しで保存するとき、必須項目が空なら保存せず、入力欄の近くにエラーを表示する。移動・状態変更などの専用操作では必須項目を検査しない（テンプレート変更で新たに必須になった項目が空のままでも実行できる）。

複製登録で引き継ぐ内容は次のとおり。

- 引き継ぐ：カテゴリ、属性、名称、保管場所、数量、タグ、備考、製品共通の識別コード
- 引き継がない：写真、個体識別の識別コード、テンプレートで「複製時にクリア」とした項目

### カテゴリとテンプレート

- カテゴリは大カテゴリ・小カテゴリの2段固定とする。小カテゴリは省略できる。
- テンプレート（入力項目の定義）は大カテゴリ・小カテゴリのどちらにも定義できる。小カテゴリの入力欄は「大カテゴリの項目＋小カテゴリで追加した項目」を合成して表示する。
- 項目ごとに次を定義する。
  - 内部キー（属性JSONのキー。例：`connector_a`）
  - 表示名
  - 型
  - 必須かどうか
  - 表示順
  - 複製時にクリアするか
  - 重複判定に使うか
  - 識別子の種類（識別コードを入力する項目の場合。種類は「識別コード」参照）
- 項目の型は次のとおり。

| 型 | 内容 |
| --- | --- |
| テキスト | 自由入力の文字列 |
| 選択候補付きテキスト | 自由入力に加え、過去の入力値を候補として表示する（例：端子） |
| 数値 | 数値のみ |
| 数値＋単位 | 数値と単位の組。フェーズ1は長さ（mm / cm / m）のみ |
| 日付 | 日付 |
| 真偽値 | はい／いいえ |

- 初期状態で用意するテンプレートは「書籍」と「ケーブル類」のみ。 それ以外は利用しながら新規カテゴリとして育てる。
  - 書籍：タイトル（名称として使う）、著者、出版社、ISBN（識別コード）
  - ケーブル類：端子A（`connector_a`）、端子B（`connector_b`）、長さ（`length`、数値＋単位）。重複判定には端子A・端子Bを使う

#### テンプレート変更時の既存データ

テンプレートを変更しても、既存の物品データは書き換えない。項目の定義は次の範囲で変更できる。

- 作成後の内部キー・型・識別子の種類は変更できない。
- 表示名・表示順・必須設定・複製時クリア設定・重複判定設定は変更できる。表示名を変えても内部キーは変わらない。
- 型や識別子の種類を変える場合は、別項目を追加し、旧項目を廃止する。項目定義は物理削除せず、廃止した内部キーは再利用しない。
- 大カテゴリと小カテゴリの項目を合成した際に、内部キーが重複する定義は許可しない。

変更後に既存の物品を開いたときは次のように扱う。

- 現在のテンプレートに従って入力欄を表示する。
- 廃止された項目の値は「テンプレート外の項目」として表示し、編集・削除できる。
- 物品のカテゴリを変更した場合も、移行先にない属性は「テンプレート外の項目」として保持する。
- 新たに必須になった項目が空の場合の扱いは「登録フロー（段階表示）」の必須項目の検査に従う。

#### ケーブル類の固定処理

フェーズ1では、ケーブル類に必要な次の処理を内部キーで固定して実装する。カテゴリ名には依存させず、内部キー `connector_a`・`connector_b`・`length` を持つテンプレートのカテゴリに適用する。テンプレートの設定として汎用化するのはフェーズ3とする。

- 名称の自動生成：端子A・端子B・長さから名称を生成する（例：`HDMI - DisplayPort 1.8m`）。生成後に修正できる。
- 名称の再生成：属性を編集したとき、現在の名称が編集前の属性から生成される名称と同じ場合だけ再生成する。手で修正した名称は上書きしない。
- 端子の比較：重複警告と集計では、`connector_a` と `connector_b` を順序を問わずに比較する（HDMI-DPとDP-HDMIは同一）。
- 長さ別の内訳：集計では端子の組み合わせでまとめ、`length` 別の内訳も表示する（例：「HDMI-DPは合計5本」の内訳として1mが2本、1.8mが3本）。

### 識別コード

- ISBN、JAN、型番、シリアル番号などの識別コードは、identifiersテーブルだけに保存し、属性JSONには保存しない。
- テンプレートの項目に識別子の種類を対応付け、登録画面では他の項目と同じように入力できるようにする。
- 識別子の種類はフェーズ1では次の固定一覧とする。種類の追加はフェーズ3以降で検討する。

| 種類 | 区分 |
| --- | --- |
| ISBN | 製品共通 |
| JAN | 製品共通 |
| 型番 | 製品共通 |
| シリアル番号 | 個体識別 |

- 個体識別の識別コードを持つ登録は数量1に限り、統合できない。製品共通の識別コードは数量付きの登録にも付けられる。

### 登録単位

- 1件の登録は「1つの保管場所・1つの状態」にある物を表す。
- 基本は1品ずつ登録する。 数が限られる物（例：HDMI-DPケーブル）を個別に把握できるようにするため。
- 大量にある物（例：HDMI-HDMI、USB A-Cケーブル）は、数量付きで1件にまとめて登録してもよい。
- 数量は1以上の整数とする。
- 分割：まとめ登録した物から、指定した数量を別の登録に切り出せる。
  - 数量Nの登録から切り出せる数量は1〜N−1とし、分割前後で数量の合計を変えない。
  - 元の登録はIDを保ったまま残りの数量を持つ。切り出した分は新しい登録とし、分割元の登録IDを保持する。
  - 切り出した登録は、カテゴリ・属性・名称・保管場所・状態・タグ・備考、その状態に付随する貸出・手放しの情報、製品共通の識別コードを引き継ぐ。写真は引き継がない。
  - 自動分割：一部の数量だけを移動・状態変更（取り出す・貸出・手放しなど）する場合は、指定した数量を自動で切り出し、切り出した登録に操作を適用する。全数量を対象とする場合は分割せず通常の操作として扱う。
- 統合：初期段階では「保管中同士」「使用中同士」の登録だけを対象とする。
  - カテゴリ・名称・全属性（テンプレート外の項目を含む）・保管場所・状態・製品共通の識別コードが一致する場合だけ許可する。
  - 識別コードは種類と値の組の集合で比較し、未入力と入力済みも不一致とする。必要な修正は統合前に行う。
  - 個体識別の識別コードを持つ登録、および有効でない登録は対象外とする。
  - 数量は合計する。写真・タグは統合先へまとめ、重複を除く。写真の用途は保持する。同じ識別コードは重複して保持しない。
  - 異なる備考は統合元の登録IDが分かる形で併記する。統合結果を確定前に表示する。
  - 統合元は統合済みとなり、統合先の登録IDを保持する。統合元とその変更履歴は残し、統合先の変更履歴から辿れるようにする。
- 分割・統合に伴う登録変更、関連情報の移動、履歴記録は、一体の操作としてすべて成功するか、すべて取り消されるかのどちらかにする。自動分割後の移動・状態変更も同じ操作に含める。

### 検索・更新

- 全文検索：対象と方式は「全文検索」を参照。
- 絞り込み：カテゴリ、保管場所、状態、タグ。
- 状態の既定の絞り込みは所持中とし、手放した物は絞り込みを変えると表示される。
- 削除済み・統合済みの登録は通常の検索に表示しない。削除済みは検索画面の「削除済みも表示」で確認できる。統合済みは統合先の変更履歴から辿る。
- 詳細画面での操作：内容の修正、移動、取り出す・戻す、貸出・返却、手放し、手放しの取消、分割、統合、写真の紐付け・紐付け解除・用途変更、履歴からの差し戻し、誤登録削除。
- 保管場所（箱）を指定して、中身の一覧を表示できる。
  - 入れ子の保管場所（箱の中の小箱など）の中身を含めるかを切り替えられる。
  - 保管中の物を基本とし、使用中・貸出中の物は「この箱に戻す物」として分けて表示する。登録件数・数量も状態別に表示する（例：「箱A-03：保管中3本／使用中1本／貸出中2本」）。
- 所在の表示：検索結果・箱の中身・重複警告・集計など所在を表示するすべての画面で、保管中の物の保管場所と、使用中・貸出中の物の戻し先を区別して表示する。

### 重複警告と集計

重複警告・集計は買い足し防止のための比較であり、登録を1件にまとめる統合よりも緩い一致条件を用いる。フェーズ1で以下を実装し、フェーズ3で強化する。

- 対象は所持中の有効な登録とする。
- 重複警告：登録時に、次のいずれかに該当する登録があれば、該当した理由ごとに登録件数・数量合計・所在を表示する。登録自体は妨げない。
  - 判定項目の一致：テンプレートで「重複判定に使う」とした項目の値がすべて一致する。
  - 製品共通の識別コードの一致：種類と値が一致する識別コードを持つ（カテゴリを問わない）。書籍のISBN一致はこれで検出する。
  - 名称の一致：同じ大カテゴリ内で、名称がNFKC正規化後に大文字・小文字と空白の違いを除いて一致する。
- 判定項目の一致の条件は次のとおり。
  - 重複判定項目が未設定、または判定項目のどれかが未入力の場合は判定しない。比較先も判定項目がすべて入力済みの登録に限る。
  - 比較範囲は、判定に使う項目を定義したカテゴリのうち最も下位のカテゴリと、その配下とする。例えば大カテゴリで定義した項目だけで判定する場合は、大カテゴリだけの登録と配下の小カテゴリの登録をまとめて比較する。
  - 数値＋単位の項目は、基準単位（長さはmm）に換算して比較する。
- 集計：判定項目の一致と同じ対象・比較範囲・条件でグループ化し、登録件数・数量合計・状態別の内訳・所在を一覧表示する。本数・個数は数量の合計とする。
- 判定項目が未設定または未入力の登録は、集計のグループに含めず、判定できない登録として区別する。
- ケーブル類の比較と内訳は「ケーブル類の固定処理」に従う。

### 状態と手放し

状態は次の5つとする。

| 状態 | 説明 | 保管場所の扱い |
| --- | --- | --- |
| 保管中 | 箱などに保管している | 保管場所を保持する |
| 使用中 | 取り出して使っている | 元の保管場所を戻し先として保持する（「戻す」で戻る） |
| 貸出中 | 他人に貸している | 元の保管場所を戻し先として保持する（「返却」で戻る） |
| 売却済 | 手放した（売却） | 空にする（直前の場所は変更履歴に残る） |
| 廃棄済 | 手放した（廃棄） | 空にする（直前の場所は変更履歴に残る） |

- 手放した物も削除せず、検索対象に残す。「何を持っていたか」を後から確認できるようにするため。
- 貸出・手放しの操作は、詳細画面の通常の位置に「貸出」「売却」「廃棄」ボタンとして配置する。
- 貸出・売却・廃棄の操作では、次の内容を同じ形の入力欄で記録する。
  - 日付
  - 相手（廃棄では省略可）
  - 備考（金額、返却予定の目安など自由記述）
- 状態遷移は次のとおり。
  - 保管中 ⇄ 使用中（取り出す／戻す）
  - 保管中・使用中 → 貸出中 → 保管中（返却。戻し先へ戻る）
  - 保管中・使用中・貸出中 → 売却済・廃棄済
  - 売却済・廃棄済 → 手放し直前の状態（手放しの取消）
- 使用中・貸出中の物を移動した場合は、戻し先の変更として扱う。
- 手放しの取消（誤操作対策）
  - 現在の売却済・廃棄済にした操作だけを対象とする。途中で備考などを編集していても、その手放し操作を特定できるようにする。
  - 対象の手放し操作の変更前から、状態・保管場所と、それに付随する貸出・手放しの日付・相手・備考を復元する。例えば「貸出中→売却済→取消」では、元の貸出日・貸出先・貸出備考も戻す。
  - 名称・属性など、それ以外の後の編集は巻き戻さない。
  - 元の手放しと取消の履歴は両方残す。
- 戻る先の保管場所が廃止済みの場合は「管理画面と廃止」に従う。

### 誤登録削除

誤って登録した物を消すための機能。手放し（特に廃棄）と混同されないよう、見た目と手順を明確に分ける。

- 詳細画面の下部など、目立たない場所に配置する。
- 押すと「廃棄・売却した場合は手放しの操作を使ってください」という案内と、削除理由の入力欄を表示する。
- 削除理由の入力と確定操作がなければ削除しない。
- 削除は論理削除（削除済みの印を付ける）とし、データは消さない。
- 削除済みの物は、検索画面の「削除済みも表示」で確認でき、そこから復元できる。

### 変更履歴

- 物品・保管場所に対するすべての変更を1つの履歴テーブルに記録する。出し入れ（移動）の履歴もこのテーブルで扱う（専用の移動履歴テーブルは設けない）。
- 変更前・変更後の内容（JSON）、日時、メモ（削除理由など）を保持する。変更前・変更後は差分ではなく、その時点の完全な内容とし、属性・タグ・識別コード・写真との対応・貸出や手放しの情報も含める。
- 操作と記録する種類の対応は次のとおり。

| 種類 | 対象の操作 |
| --- | --- |
| 登録 | 物品の登録・複製登録、保管場所の作成 |
| 修正 | 内容の修正、写真の紐付け・紐付け解除・用途変更、タグの統合に伴う紐付け変更、履歴からの差し戻し、保管場所の名称・種類の変更、保管場所の廃止・廃止の取消 |
| 移動 | 物品の移動（戻し先の変更を含む）、保管場所の親の変更 |
| 状態変更 | 取り出す・戻す・貸出・返却・売却・廃棄・手放しの取消 |
| 分割 | 分割・自動分割（元の登録と切り出した登録の両方に記録） |
| 統合 | 統合（統合先と統合元の両方に記録） |
| 削除 | 誤登録削除 |
| 復元 | 誤登録削除からの復元 |

#### 履歴からの差し戻し

誤って上書きした説明情報を戻すための操作。

- 物品の履歴を1件選び、その「変更前」にある名称・属性・タグ・備考だけを差し戻せるようにする。
- 現在との差分を表示し、確認後に新しい修正として適用する。後の履歴は書き換えない。
- 差し戻せるのは上記4項目に限る。数量・状態・保管場所・削除状態・分割や統合の関係・カテゴリ・識別コード・写真などは対象外とし、それぞれの編集・専用操作で扱う。
- 差し戻すタグが統合済みの場合は統合先のタグに読み替える。廃止済みのタグはそのまま戻し、差分表示で廃止済みであることを示す。

### 保管場所とラベル

- 保管場所は階層構造とし、「部屋 › 家具 › 段 › 箱」まで表現できるようにする。箱の中の小箱のような入れ子も許容する。
- 保管場所の種類は初期状態で「部屋・家具・段・箱」を用意し、管理画面から追加できる。
- 箱を別の場所へ移した場合は、箱1件の移動として記録する（中身の物品ごとの履歴は作らない）。
- 保管場所を、自分自身またはその配下の保管場所の中へは移動できない。
- 箱のIDは短い英数字の連番とする（例：`A-01`）。
- 当面は文字だけのラベルで運用する。 手持ちのラベルライター（Brother PT-P300BT、12mm幅テープ、スマホアプリ専用）で印字する。
- IDは将来QRコード化できる形式にしておく。将来の選択肢は次のとおり（今は実装不要）。
  - Brother PT-P710BT（PC用ソフトでQRコード作成可、24mm幅まで対応）
  - 家庭用プリンタとA4ラベルシール（ツールから印刷用ページを出力）

### 管理画面と廃止

- 管理画面は一般的な一覧＋編集フォームの構成でよく、入力しやすさを優先する。
- カテゴリとテンプレート、タグ、保管場所について、作成・名称変更・廃止・廃止の取消を行える。タグは統合もできる。
- 廃止済みのものは新規選択の候補に表示しない。既存の紐付けは残し、詳細画面では廃止済みであることを表示する。
- 廃止できる条件は次のとおり。
  - 保管場所：保管場所として参照する保管中の有効な登録と、有効な子の保管場所がない場合に限る。戻し先としてだけ参照されている場合は廃止できる。
  - カテゴリ：有効な小カテゴリがない場合に限る。既存の登録はそのカテゴリのまま残る。
  - タグ・項目定義：常に廃止できる。
- 保管場所の選び直し：戻す・返却・手放しの取消・誤登録削除からの復元で、戻る先の保管場所が廃止済みの場合は、有効な保管場所を選んでから確定する。使用中・貸出中に戻す場合は、選んだ場所を新たな戻し先とする。元の場所と選び直した場所は変更履歴に残す。
- タグの統合：削除済み・統合済みを含む全登録の紐付けを統合先へ移し、重複を除いて統合元を廃止する。統合元のタグは統合先を保持する。過去の変更履歴は書き換えない。

### 写真

- ブラウザからファイルを選択してアップロードする方式で取り込む。
- 取り込み時に、ツール専用の画像フォルダへコピーする（元の写真フォルダが移動・削除されても影響を受けない）。
- iPhoneで撮影したHEIC形式に対応する。元ファイルはそのまま保存し、閲覧用にはブラウザで表示できる形式の画像を生成する。
- 閲覧用の縮小版を生成する。生成時は撮影時の向き（EXIFの回転情報）を反映する。
- ファイル内容のハッシュで同じ写真の二重取り込みを検知し、警告する。
- 写真は物品または保管場所に紐付け、用途（表紙、裏表紙、正面、裏面、箱の中身全体など）を区別する。
- 紐付けの解除と用途の変更ができる。解除しても画像ファイルは削除せず、変更履歴から辿れるようにする。写真の差し替えは、紐付けの解除と新しい写真の取り込みで行う。

### バックアップとエクスポート

バックアップはアプリを元どおり動かすための復元用、CSVは閲覧・集計用、JSONはツールに依存せずデータを持ち出すための出力とする。

#### バックアップ

- 手動で実行し、DBと画像フォルダを日付付きのzipにまとめ、任意の場所（外付けドライブやNASなど）に書き出す。
- バックアップ中は更新・写真取り込みを一時停止し、閲覧のみ許可する。DBはSQLiteのバックアップ機能でコピーし、DBと画像を整合した組として書き出す。
- バックアップの成功条件は次のとおり。
  - 画像フォルダの元画像をすべて含む（削除済み・統合済みの登録や紐付けを解除した写真の画像も含む）。
  - 閲覧用画像を含むか、復元後に元画像から再生成できる。
  - アプリのバージョン・DB形式のバージョン・作成日時が分かる。
  - 途中で失敗したzipを完成したバックアップとして扱わない。成功と表示するのは、必要な内容を含めて書き出しが完了した場合だけとする。
- 復元手順を用意する（ツールを停止し、バックアップを展開してDBと画像フォルダを置き換える）。
- バックアップの検証では、展開したDBと画像から物品・履歴・写真を参照できることを確認する。

#### DB形式のバージョン

- 起動時にDB形式のバージョンを確認する。バックアップから復元したDBにも同じ扱いを適用する。
- アプリより古い形式の場合は、元のDBを退避してからマイグレーションする。
- アプリより新しい形式の場合は起動せず、理由を表示する。

#### エクスポート

- CSVはExcelで開けるようBOM付きUTF-8とし、1行に1件の登録を出力する。
  - 登録ID・名称・カテゴリ・数量・状態・所在（保管場所の階層。戻し先であるかが分かる形）・属性・識別コード・タグ・備考を含める。
  - 属性は項目定義ごとに1列とし、列名は「項目を定義したカテゴリ名：表示名」とする。テンプレート外の項目も列に含める。数値＋単位は「1.8 m」のように値と単位を1セルに出力する。
  - 識別コード・タグなど1件に複数ある値は、1セルに区切り文字（` | `）で並べる。識別コードは「種類:値」の形で出力する。
  - 写真との対応はCSVに含めず、JSONで扱う。
- JSONは物品とその履歴、カテゴリ、テンプレート、保管場所とその履歴、タグ、識別コード、写真との対応情報を含め、出力形式のバージョンを付ける。
  - 属性の意味やデータ同士の関係が分かるよう、内部キー・定義・IDを保持する。
  - JSONと対応する画像の実体をまとめて持ち出せる出力を用意する。画像との対応は出力内で辿れるようにする。
- 削除済みの物を含めるかを選べる。選択した出力範囲の履歴や関連情報を解釈できるようにし、過去の参照先や廃止済みの定義も必要な範囲で保持する。

## 非機能要件

- 利用者は1人とする。
- 当面は `127.0.0.1` のみで待ち受け、認証は設けない。
- 同一LAN内のスマホから利用する場合（フェーズ4）は、公開範囲を広げるのに合わせて認証を追加する。

## データ設計（概念レベル）

テーブル定義の詳細（列・型・制約・インデックス）はClaude Codeで作成する。以下は役割の整理である。

| テーブル | 役割 | 主な項目 |
| --- | --- | --- |
| items | 管理対象の物品すべて | 名称、カテゴリ、数量（正の整数）、状態、保管場所（使用中・貸出中は戻し先）、備考、属性（JSON）、直近の貸出・手放しの日付・相手・備考、現在の手放し操作を特定する情報、削除済みフラグ・削除日時、分割元、統合先 |
| identifiers | 物品に付く識別コード（1物品に複数可） | 種類（区分は種類で決まる）、値 |
| categories | 2段の分類 | 名称、親カテゴリ、廃止状態 |
| category_fields | カテゴリごとの入力テンプレート | 内部キー、表示名、型、単位、必須、表示順、複製時クリア、重複判定、識別子の種類、廃止状態 |
| tags / item_tags | 分類をまたぐ目印と物品への紐付け | 名称（例：「売却候補」「思い出の品」）、廃止状態、統合先、物品との対応 |
| containers | 部屋・家具・段・箱を一元管理 | 名称、種類、親、ラベルID、廃止状態 |
| photos | 物品・保管場所の画像 | ファイルパス、縮小版パス、ハッシュ、用途、紐付け先、紐付け解除の状態 |
| item_events | 全変更の履歴（物品・保管場所） | 対象、種類、変更前、変更後（JSON）、日時、メモ |
| lookup_cache | 外部照会結果のキャッシュ | コード、照会先、取得データ（生JSON）、取得日時 |

### JSON属性について

カテゴリごとに異なる項目（書籍の著者、ケーブルの端子など）は、itemsテーブルの1つの列（`attributes`）にJSONで保持する。キーは表示名ではなく内部キーとし、数値＋単位の項目は数値と単位の組で保持する。

```txt
書籍:     {"author": "…", "publisher": "…"}
ケーブル: {"connector_a": "HDMI", "connector_b": "DisplayPort", "length": {"value": 1.8, "unit": "m"}}
```

- カテゴリごとに列を増やさずに済む。
- SQLiteのJSON関数で、属性による絞り込みや集計ができる（重複警告や件数集計に使う）。
- 入力欄の定義はcategory_fieldsが持ち、値はattributesが持つという分担とする。

### 全文検索

- SQLiteのFTS5を用い、名称・備考・属性・識別コード・貸出や手放しの相手と備考を横断して検索できるようにする。
- 日本語は標準のトークナイザーで単語に区切れないため、`trigram` トークナイザーを使う。
- `trigram` は3文字未満の語で索引を使えないため、2文字以下の検索語はLIKEによる部分一致で検索する。
- 索引と検索語は、全角・半角の違いを吸収するためNFKCで正規化する。

### 照会結果のキャッシュ

外部照会の結果はコード単位でlookup_cacheに保存する。同じ物を複数登録しても照会は1回で済み、照会先のサービスが終了しても取得済みの情報は残る。

## 開発の進め方

段階的に機能を追加する。フェーズ1は4段階に分ける。

- テーブル定義はフェーズ1-1で、フェーズ1全体（分割元・統合先・廃止状態など）を見越して設計し、以降の段階で大きなマイグレーションが起きないようにする。
- 変更履歴はフェーズ1-1から記録する。後から過去の履歴を補うことはできないため。

1. フェーズ1-1：登録と検索の基盤
   カテゴリ・テンプレート、保管場所、タグ、管理画面での作成・名称変更、物品の登録（段階表示・クリアボタン・複製登録）、識別コード、ケーブル類の固定処理、検索・更新（全文検索・絞り込み・箱の中身）、写真の取り込み（HEIC対応、紐付け解除・用途変更を含む）、変更履歴の記録。
2. フェーズ1-2：状態管理と復旧
   状態と手放し（手放しの取消を含む）、誤登録削除と復元、履歴からの差し戻し、手動バックアップと復元、DB形式のバージョン確認。
3. フェーズ1-3：重複警告・集計と分割・統合
   重複警告と集計（「重複警告と集計」に記載した範囲）、物品の分割・自動分割・統合。
4. フェーズ1-4：管理機能の拡張とエクスポート
   廃止・廃止の取消、タグの統合、CSV・JSONと画像のエクスポート。
5. フェーズ2：バーコード読み取りとISBN照会
   画像からのバーコード読み取り、ISBN照会（照会先の差し替え機構とキャッシュ）、書籍の自動入力。
6. フェーズ3：JAN照会とラベル関連
   JAN照会（取得できれば利用する程度）、重複警告と集計の強化（ケーブル類の固定処理のテンプレート設定化を含む）、数値＋単位の単位の種類と識別子の種類の追加、ラベル用ID一覧の出力。
7. フェーズ4（任意）
   ローカル文字認識、スマホからの利用（LAN内アクセスと認証）、QRコードラベル。

## 外部連携

### ISBN照会

- 照会先は差し替え可能な構成にする（プロバイダ方式）。
- 第一候補：国立国会図書館サーチ。予備：openBDの後継API、Google Books など。
- 参考：openBDは2023年7月に「openBD API（バージョン1）」の提供終了を発表しており、代替APIは収録範囲・内容が変わるとされている。照会先の最新状況は実装時に確認すること。

### JAN照会

- 無料で安定した照会先が少ないため、「コードは必ず保存し、製品情報は取得できれば利用する」程度の位置付けとする。

### バーコード読み取り

- ローカルで処理する（候補：zxing-cppなど）。

### 文字認識

- ローカル専用（候補：NDLOCRなど）。クラウドAIは使用しない。
- 優先度は低い。ISBN/JANが読み取れれば十分という位置付け。
