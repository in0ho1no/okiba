# 私物管理ツール 仕様書

本書は、claude.ai上での仕様検討の結果に、Claude Codeでの仕様レビュー（2026年10月）の決定事項を反映したものです。以降の設計・実装はローカルPC上のClaude Codeで行います。

---

## 目的

私物（書籍、PC関連品、文具など多岐にわたる物品）について、次のことを容易にする。

- どの箱がどこに保管されているか、箱の中身は何かを把握する
- 出し入れ・移動・手放し（貸出・売却・廃棄）の際に記録を更新する
- 後から「何を持っていたか」「どこにあるか」「何本持っているか」を検索する
- 在庫の把握により、既に持っている物を無駄に買い足すことを防ぐ

## 前提と基本方針

- ローカルPCで動作するツールとする。 claude.aiなど特定サービス上には構築しない（契約依存・サービス終了のリスクを避けるため）。
- 形態はローカルWebアプリ（Pythonのサーバー＋ブラウザ）。当面はPCのブラウザから利用する。将来、同一LAN内のスマホから利用できる余地を残す。
- データはSQLite＋画像フォルダで保持し、CSV/JSONへのエクスポートを可能にする。ツールが使えなくなってもデータが残ることを重視する。
- 写真の入手経路：スマホ（主にiPhone）で撮影 → Google Photos → PCにダウンロードしたフォルダから取り込む。Google PhotosのAPIには依存しない。
- 外部サービスへの依存は最小限にし、差し替え可能にする（詳細は「外部連携」）。
- 開発者は Python ツールチェーン（uv, ruff, mypy, pytest）の利用経験あり。これを前提に構成してよい。

## やらないこと（検討の結果、見送った事項）

| 項目 | 理由 |
| --- | --- |
| 背表紙写真などからの一括登録 | 1品ずつ画像を残す運用の方が効率的。一括読み取り→確認→追記は二重作業になるため |
| クラウドAIによる文字認識 | 私物の写真を外部に送らない。サービス依存も避ける。文字認識自体も本命ではない |
| 自動バックアップ | 容量の逼迫や処理のボトルネック化を避けるため。手動で行う |
| 通常操作での物理削除 | 誤操作防止と履歴保全のため。誤登録削除は論理削除とする |
| 初期段階でのQRコードラベル | 当面PC利用のため読み取る場面が少ない。文字ラベルで運用する |
| 既存リストからの一括取り込み | 既存の私物をリストで管理していないため |

## 機能要件

### 画面構成

最上位で次の3つを切り替える。

- 登録
- 検索・更新（検索結果から詳細画面を開き、修正・移動・手放し・分割・統合・誤登録削除を行う）
- 管理（カテゴリとテンプレート、タグ、保管場所の作成・名称変更・統合・廃止）

管理画面は一般的な一覧＋編集フォームの構成でよく、入力しやすさを優先する。

### 登録フロー（段階表示）

入力を進めるごとに次の項目が表示される方式とする。

1. 大カテゴリを選択：過去の登録履歴から候補を表示。該当がなければ新規カテゴリを作成。
2. 小カテゴリを選択：同上。小カテゴリは省略できる（大カテゴリのみで登録可）。
3. カテゴリ別の詳細入力：カテゴリに紐付くテンプレート（「カテゴリとテンプレート」参照）に従って入力欄を表示。
4. 共通項目：名称（必須）、保管場所（必須）、数量（既定値1）、タグ、備考。
5. 登録：「登録」または「登録して同じ内容で続ける」（複製登録）。

名称の扱いは次のとおり。

- 名称は全カテゴリ共通の必須項目とする。
- 書籍はタイトルを名称として使う（タイトル欄と名称欄を兼ねる）。
- ケーブル類は属性から名称を自動生成する（例：`HDMI - DisplayPort 1.8m`）。生成後に修正できる。

カテゴリ別の流れの例は次のとおり。フェーズ1は手入力のみとし、画像からの読み取りと照会はフェーズ2以降で追加する。

- 書籍
  1. 画像を取り込む（表紙・裏表紙）
  2. 裏表紙のバーコードからISBNを読み取り、書誌情報を照会（フェーズ2）
  3. 照会成功 → タイトル・著者・出版社などを自動入力（修正可）
  4. 照会失敗 → 各入力欄を表示して手入力（ISBNは任意入力）
- ケーブル類
  1. 端子A、端子B、長さを手入力（端子は過去の入力値から選択可能にする）
  2. 画像は任意
  3. 同じ属性の組み合わせが既に登録されていれば、件数と所在を表示する（重複警告。例：「同じ端子の組み合わせを2本登録済み（箱A-03、箱B-01）」）。判定方法は「重複警告と集計」を参照
- 新規カテゴリ
  1. 画像を取り込む
  2. 製品バーコード（JAN）を読み取り、照会（フェーズ3）
  3. 照会成功 → 名称・メーカーなどを自動入力
  4. 照会失敗 → 最低限の入力欄（名称）を表示
  5. 入力欄が足りなければ「項目を追加」で任意の項目を追加
  6. 追加した項目は、そのカテゴリのテンプレートとして保存できる（既定でオン）

入力補助として、次の機能を設ける。

- 各入力欄にクリアボタン（×）を付ける。 複製登録時に、残したい部分は流用し、変えたい欄だけ消して打ち直せるようにする。
- 複製時に自動で空にする項目をテンプレートで指定できる（シリアル番号など、1品ごとに必ず異なる項目）。
- 必須項目が空の場合は登録せず、入力欄の近くにエラーを表示する。

複製登録で引き継ぐ内容は次のとおり。

- 引き継ぐ：カテゴリ、属性（複製時クリアの項目を除く）、名称、保管場所、数量、タグ、備考
- 引き継がない：写真、識別コード

### カテゴリとテンプレート

- カテゴリは大カテゴリ・小カテゴリの2段固定とする。小カテゴリは省略できる。
- テンプレート（入力項目の定義）は大カテゴリ・小カテゴリのどちらにも定義できる。小カテゴリの入力欄は「大カテゴリの項目＋小カテゴリで追加した項目」を合成して表示する。
- 項目ごとに次を定義する。
  - 内部キー（属性JSONのキー。例：`connector_a`）
  - 表示名（変更可能。変更しても内部キーは変わらない）
  - 型
  - 必須かどうか
  - 表示順
  - 複製時にクリアするか
  - 重複判定に使うか
  - 識別子の種類（識別コードを入力する項目の場合。例：ISBN、シリアル）
- 項目の型は次のとおり。

| 型 | 内容 |
| --- | --- |
| テキスト | 自由入力の文字列 |
| 選択候補付きテキスト | 自由入力に加え、過去の入力値を候補として表示する（例：端子） |
| 数値 | 数値のみ |
| 数値＋単位 | 数値と単位の組。長さの単位は mm / cm / m から選ぶ |
| 日付 | 日付 |
| 真偽値 | はい／いいえ |

- 初期状態で用意するテンプレートは「書籍」と「ケーブル類」のみ。 それ以外は利用しながら新規カテゴリとして育てる。
  - 書籍：タイトル（名称として使う）、著者、出版社、ISBN（識別コード）
  - ケーブル類：端子A、端子B、長さ（数値＋単位）。重複判定には端子A・端子Bを使う

#### テンプレート変更時の既存データ

テンプレートを変更しても、既存の物品データは書き換えない。変更後に既存の物品を開いたときは次のように扱う。

- 現在のテンプレートに従って入力欄を表示する。
- テンプレートから削除された項目の値は「テンプレート外の項目」として表示し、編集・削除できる。
- 新たに必須になった項目が空の場合は、保存しようとしたときに入力欄の近くにエラーを表示する。

### 識別コード

- ISBN、JAN、型番、シリアル番号などの識別コードは、identifiersテーブルだけに保存し、属性JSONには保存しない。
- テンプレートの項目に識別子の種類を対応付け、登録画面では他の項目と同じように入力できるようにする。

### 登録単位

- 1件の登録は「1つの保管場所・1つの状態」にある物を表す。
- 基本は1品ずつ登録する。 数が限られる物（例：HDMI-DPケーブル）を個別に把握できるようにするため。
- 大量にある物（例：HDMI-HDMI、USB A-Cケーブル）は、数量付きで1件にまとめて登録してもよい。
- 分割：まとめ登録した物から、指定した数量を別の登録に切り出せる。
  - 一部の数量だけを移動・状態変更（貸出・使用中・手放しなど）した場合は、その数量を自動で切り出してから操作する。
  - 切り出した登録は、カテゴリ・属性・名称・タグ・備考を引き継ぐ。写真と識別コードは引き継がない。
- 統合：同じカテゴリ・属性・保管場所・状態の登録同士を1件にまとめられる。
  - 数量は合計する。統合元の写真・識別コード・タグは統合先へ移す。
  - 統合元は通常の検索に表示しないが、変更履歴から辿れるようにする。

### 検索・更新

- 全文検索：名称、備考、カテゴリ別の属性、識別コード（ISBN/JAN/型番など）を対象とする（方式は「全文検索」を参照）。
- 絞り込み：カテゴリ、保管場所、状態、タグ。
- 状態の既定の絞り込みは「保管中・使用中・貸出中」とし、手放した物（売却済・廃棄済）は絞り込みを変えると表示される。
- 詳細画面での操作：内容の修正、保管場所の移動（出し入れ）、手放し、手放しの取消、分割、統合、誤登録削除。
- 保管場所（箱）を指定して、中身の一覧を表示できる。入れ子の保管場所（箱の中の小箱など）の中身を含めるかを切り替えられる。

### 重複警告と集計

フェーズ1で最低限の機能を実装し、フェーズ3で強化する。

- 重複警告：登録時に、テンプレートで「重複判定に使う」とした項目の値がすべて一致する登録が既にあれば、件数と所在を表示する。登録自体は妨げない。
- ケーブル類の端子A・端子Bは、順序を入れ替えた組み合わせも同じとみなす（HDMI-DPとDP-HDMIは同一）。
- 数値＋単位の項目は、基準単位（長さはmm）に換算して比較する。
- 集計：同じ属性の物品の件数と所在の一覧（例：「HDMI-DPケーブルは全部で何本、どの箱に」）。本数・個数は数量の合計とする。

### 状態と手放し

状態は次の5つとする。

| 状態 | 説明 | 保管場所 |
| --- | --- | --- |
| 保管中 | 箱などに保管している | 現在の保管場所 |
| 使用中 | 取り出して使っている | 元の保管場所を保持する（「戻す」で元の場所へ戻る） |
| 貸出中 | 他人に貸している | 元の保管場所を保持する（「返却」で元の場所へ戻る） |
| 売却済 | 手放した（売却） | 空にする（直前の場所は変更履歴に残る） |
| 廃棄済 | 手放した（廃棄） | 空にする（直前の場所は変更履歴に残る） |

- 手放した物（売却済・廃棄済）も削除せず、検索対象に残す。「何を持っていたか」を後から確認できるようにするため。
- 手放しの操作は、詳細画面の通常の位置に「貸出」「売却」「廃棄」ボタンとして配置する。
- 貸出・売却・廃棄の操作では、次の内容を同じ形の入力欄で記録する。
  - 日付
  - 相手（廃棄では省略可）
  - 備考（金額、返却予定の目安など自由記述）
- 状態遷移は次のとおり。
  - 保管中 ⇄ 使用中（取り出す／戻す）
  - 保管中・使用中 → 貸出中 → 保管中（返却。元の保管場所へ戻る）
  - 保管中・使用中・貸出中 → 売却済・廃棄済
  - 売却済・廃棄済 → 手放し直前の状態（取消）
- 手放しの取消（誤操作対策）：売却済・廃棄済を取り消すと、状態は手放し直前の状態に、保管場所は変更履歴から直前の場所に戻る。取消も状態変更として変更履歴に記録する。

### 誤登録削除

誤って登録した物を消すための機能。手放し（特に廃棄）と混同されないよう、見た目と手順を明確に分ける。

- 詳細画面の下部など、目立たない場所に配置する。
- 押すと「廃棄・売却した場合は手放しの操作を使ってください」という案内と、削除理由の入力欄を表示する。
- 削除理由の入力と確定操作がなければ削除しない。
- 削除は論理削除（削除済みの印を付ける）とし、データは消さない。
- 削除済みの物は通常の検索に表示しない。検索画面の「削除済みも表示」で確認でき、そこから復元できる。
- 削除・復元の操作も変更履歴（「変更履歴」参照）に記録する。

### 変更履歴

- 物品・保管場所に対するすべての変更を1つの履歴テーブルに記録する。
- 記録する種類：登録、修正、移動、状態変更（手放し・取消等）、分割、統合、削除、復元。
- 変更前・変更後の内容（JSON）、日時、メモ（削除理由など）を保持する。変更前・変更後は差分ではなく、その時点の完全な内容とする。
- 誤削除だけでなく、誤って上書きした内容も変更前の状態から戻せるようにする。履歴を1件選び、その「変更前」の内容を新しい修正として適用する方式とする（後の変更を巻き戻すのではなく、戻した操作も履歴に残る）。
- 出し入れ（移動）の履歴もこのテーブルで扱う（専用の移動履歴テーブルは設けない）。

### 保管場所とラベル

- 保管場所は階層構造とし、「部屋 › 家具 › 段 › 箱」まで表現できるようにする。箱の中の小箱のような入れ子も許容する。
- 保管場所の種類は初期状態で「部屋・家具・段・箱」を用意し、管理画面から追加できる。
- 物品の登録時は保管場所を必須とする。
- 箱を別の場所へ移した場合は、箱1件の移動として記録する（中身の物品ごとの履歴は作らない）。
- 箱のIDは短い英数字の連番とする（例：`A-01`）。
- 当面は文字だけのラベルで運用する。 手持ちのラベルライター（Brother PT-P300BT、12mm幅テープ、スマホアプリ専用）で印字する。
- IDは将来QRコード化できる形式にしておく。将来の選択肢は次のとおり（今は実装不要）。
  - Brother PT-P710BT（PC用ソフトでQRコード作成可、24mm幅まで対応）
  - 家庭用プリンタとA4ラベルシール（ツールから印刷用ページを出力）

### 写真

- ブラウザからファイルを選択してアップロードする方式で取り込む。
- 取り込み時に、ツール専用の画像フォルダへコピーする（元の写真フォルダが移動・削除されても影響を受けない）。
- iPhoneで撮影したHEIC形式に対応する。元ファイルはそのまま保存し、閲覧用にはブラウザで表示できる形式の画像を生成する。
- 閲覧用の縮小版を生成する。生成時は撮影時の向き（EXIFの回転情報）を反映する。
- ファイル内容のハッシュで同じ写真の二重取り込みを検知し、警告する。
- 写真は物品または保管場所に紐付け、用途（表紙、裏表紙、正面、裏面、箱の中身全体など）を区別する。

### バックアップとエクスポート

- バックアップは手動のみ。 DBと画像フォルダを日付付きのzipにまとめ、任意の場所（外付けドライブやNASなど）に書き出す。
- DBはSQLiteのバックアップ機能でコピーし、ツールの動作中でも整合した状態で書き出す。
- 復元手順を用意する（ツールを停止し、バックアップを展開してDBと画像フォルダを置き換える）。
- エクスポート：物品一覧などをCSV/JSONで出力する。
  - CSVはExcelで開けるようBOM付きUTF-8とする。
  - カテゴリ別の属性は列に展開する。
  - 削除済みの物を含めるかを選べる。

## 非機能要件

- 利用者は1人とする。
- 当面は `127.0.0.1` のみで待ち受け、認証は設けない。
- 同一LAN内のスマホから利用する場合（フェーズ4）は、公開範囲を広げるのに合わせて認証を追加する。

## データ設計（概念レベル）

テーブル定義の詳細（列・型・制約・インデックス）はClaude Codeで作成する。以下は役割の整理である。

| テーブル | 役割 | 主な項目 |
| --- | --- | --- |
| items | 管理対象の物品すべて | 名称、カテゴリ、数量、状態、現在の保管場所、備考、属性（JSON）、直近の貸出・手放しの日付・相手・備考、削除済みフラグ・削除日時、統合先 |
| identifiers | 物品に付く識別コード（1物品に複数可） | 種類（ISBN/JAN/型番/シリアル等）、値 |
| categories | 2段の分類 | 名称、親カテゴリ |
| category_fields | カテゴリごとの入力テンプレート | 内部キー、表示名、型、単位、必須、表示順、複製時クリア、重複判定、識別子の種類 |
| tags / item_tags | 分類をまたぐ目印 | 例：「売却候補」「思い出の品」 |
| containers | 部屋・家具・段・箱を一元管理 | 名称、種類、親、ラベルID |
| photos | 物品・保管場所の画像 | ファイルパス、縮小版パス、ハッシュ、用途、紐付け先 |
| item_events | 全変更の履歴（物品・保管場所） | 対象、種類、変更前、変更後（JSON）、日時、メモ |
| lookup_cache | 外部照会結果のキャッシュ | コード、照会先、取得データ（生JSON）、取得日時 |

### JSON属性について

カテゴリごとに異なる項目（書籍の著者、ケーブルの端子など）は、itemsテーブルの1つの列（`attributes`）にJSONで保持する。キーは表示名ではなく内部キーとし、数値＋単位の項目は数値と単位の組で保持する。

```txt
書籍:     {"author": "…", "publisher": "…"}
ケーブル: {"connector_a": "HDMI", "connector_b": "DisplayPort", "length": {"value": 1.8, "unit": "m"}}
```

- カテゴリごとに列を増やさずに済む。
- SQLiteのJSON関数で、属性による絞り込みや集計ができる（重複警告や件数集計に使う）。
- 入力欄の定義はcategory_fieldsが持ち、値はattributesが持つという分担とする。
- 表示名を変更しても、内部キーが変わらないため既存データに影響しない。

### 全文検索

- SQLiteのFTS5を用い、名称・備考・属性・識別コードを横断して検索できるようにする。
- 日本語は標準のトークナイザーで単語に区切れないため、`trigram` トークナイザーを使う。
- `trigram` は3文字未満の語で索引を使えないため、2文字以下の検索語はLIKEによる部分一致で検索する。
- 索引と検索語は、全角・半角の違いを吸収するためNFKCで正規化する。

### 照会結果のキャッシュ

外部照会の結果はコード単位でlookup_cacheに保存する。同じ物を複数登録しても照会は1回で済み、照会先のサービスが終了しても取得済みの情報は残る。

## 開発の進め方

段階的に機能を追加する。

1. フェーズ1：管理と検索（手入力）
   カテゴリ・テンプレート、保管場所、タグ、管理画面、物品の登録（段階表示・クリアボタン・複製登録）、分割・統合、検索・更新、重複警告と集計（最低限）、手放しと取消、誤登録削除と復元、変更履歴、写真の取り込み（HEIC対応を含む）、手動バックアップ、エクスポート。
2. フェーズ2：バーコード読み取りとISBN照会
   画像からのバーコード読み取り、ISBN照会（照会先の差し替え機構とキャッシュ）、書籍の自動入力。
3. フェーズ3：JAN照会とラベル関連
   JAN照会（取得できれば利用する程度）、重複警告と集計の強化、ラベル用ID一覧の出力。
4. フェーズ4（任意）
   ローカル文字認識、スマホからの利用（LAN内アクセスと認証）、QRコードラベル。

## 外部連携

### ISBN照会

- 照会先は差し替え可能な構成にする（プロバイダ方式）。
- 第一候補：国立国会図書館サーチ。予備：openBDの後継API、Google Books など。
- 参考：openBDは2023年7月に「openBD API（バージョン1）」の提供終了を発表しており、代替APIは収録範囲・内容が変わるとされている。照会先の最新状況は実装時に確認すること。

### JAN照会

- 無料で安定した照会先が少ないため、「コードは必ず保存し、製品情報は取得できれば利用する」程度の位置付けとする。

### バーコード読み取り

- ローカルで処理する（候補：zxing-cppなど）。

### 文字認識

- ローカル専用（候補：NDLOCRなど）。クラウドAIは使用しない。
- 優先度は低い。ISBN/JANが読み取れれば十分という位置付け。

- テスト方針
